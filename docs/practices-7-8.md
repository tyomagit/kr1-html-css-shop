# Пояснения к практикам 7 и 8

Практики продолжают проект после занятий 1–6. В практике 7 изменена организация
HTML-классов и CSS. В практике 8 добавлены недостающие страницы и проверен сценарий
«каталог → описание → заявка». Исходное оформление, Flex/Grid и кнопка «Наверх» сохранены.

## Что изменилось в коде

**Практика 7.** У шапки появились `site-header__inner` и `site-header__logo`,
у меню — `site-nav__item`, `site-nav__link` и `site-nav__link--active`.
Селекторы вроде `.site-nav__list a` заменены прямыми классами. Аналогично
переименованы поля формы, её кнопки, элементы фильтров и хлебных крошек.
Общие кнопки получили модификаторы `button--primary` и `button--secondary`.
JavaScript находит кнопки заказа по `[data-product]`: переименование CSS-класса
не меняет их действие. Пример аудита «было → стало» находится в README.

**Практика 8.** На `product.html` добавлены описания трёх товаров и таблица с
`caption`, `thead`, `tbody`, `th`, `td` и `scope`. На `order.html` размещена форма.
Общее меню теперь связывает пять страниц. Ссылки «Подробнее» ведут к конкретному
товару через якорь. Быстрая заявка работает на главной, в каталоге и в описании товара;
форма показывает выбранный товар. Скрипт проверяет наличие формы и диалога,
поэтому на странице контактов не возникает обращения к отсутствующим элементам.

Для самостоятельной доработки добавлены FAQ без JavaScript, бейджи, сравнение
комплектаций, видимый выбранный товар, подсказки и исправляемые состояния ошибок.
Данные формы проверяются локально; backend и настоящий заказ не реализованы.

## Как устроен JavaScript

`if (orderDialog)` ограничивает работу с диалогом страницами, где он есть.
При нажатии кнопки с `data-product` форма сбрасывается, затем выбираются товар
и тема и вызывается `showModal()`. Кнопка закрытия вызывает `close()`, Escape
обрабатывается браузером автоматически.

Обработчик `submit` отменяет реальную отправку через `preventDefault()`.
`checkValidity()` проверяет ограничения HTML: `required`, `minlength`,
`type="email"` и `pattern`. Неверные поля получают `aria-invalid="true"`
и БЭМ-модификатор ошибки. `reportValidity()` показывает подсказку браузера.
Если всё верно, форма сбрасывается, диалог закрывается и показывается статус.
Это минимальная поддержка формы из предыдущих практик, а не полноценный магазин.

## Ответы к практике 7

1. **Что означает БЭМ?** Блок, элемент, модификатор.
2. **Что такое блок?** Независимый компонент, например `product-card`.
3. **Что такое элемент?** Часть блока, например `product-card__price`.
4. **Что такое модификатор?** Вариант или состояние: `product-card--discount`.
5. **Как записывается элемент?** `block__element`, через два подчёркивания.
6. **Как записывается модификатор?** `block--modifier` или `block__element--modifier`.
7. **Зачем самостоятельность блока?** Чтобы его можно было перенести в другое место без переписывания стилей.
8. **Почему элемент связан с блоком?** Его назначение определяется компонентом, частью которого он является.
9. **Почему плохи `red`, `big`, `left`?** Они описывают вид, который может измениться, и не объясняют назначение.
10. **Почему не стилизуем через `id`?** У него высокая специфичность и он должен быть уникальным; класс удобнее переиспользовать.
11. **Чем мешают inline-стили?** Смешивают разметку с оформлением и затрудняют общее изменение компонента.
12. **Как БЭМ уменьшает вложенность?** Вместо цепочки родительских тегов задаётся прямой класс элемента.
13. **Почему карточка — блок?** Она повторяется на главной и в каталоге с тем же оформлением.
14. **Почему кнопка — отдельный блок?** Она используется в карточке, форме, ссылке наверх и других местах.
15. **Почему форма и диалог — разные блоки?** Форма также нужна на отдельной странице без диалога.
16. **Что проверять в JS после переименования?** Поиск элементов, открытие/закрытие диалога, подстановку товара и проверку формы.
17. **Как понять, что рефакторинг успешен?** Имена последовательны, компоненты независимы, прежние функции и оформление работают.

## Ответы к практике 8

1. **Зачем отдельный репозиторий каждой КР?** Чтобы отдельно хранить исходники, историю и результат каждой технологии.
2. **Чем многостраничный сайт отличается от одностраничного?** У него несколько HTML-документов с собственными URL и содержимым.
3. **Какие страницы обязательны?** Главная, каталог, товар, заявка, контакты.
4. **Зачем единая навигация?** Чтобы с каждой страницы были доступны основные разделы.
5. **Зачем якоря?** Чтобы перейти к элементу с соответствующим `id`, в том числе на другой странице.
6. **Зачем семантические теги?** Они описывают назначение частей страницы для людей, браузера и вспомогательных технологий.
7. **Почему один `main`?** Он обозначает единственную основную область содержимого текущей страницы.
8. **Для чего `article`?** Для самостоятельного фрагмента, например карточки товара.
9. **Зачем таблица?** Для сравнения характеристик по одинаковым параметрам.
10. **Зачем форма?** Для ввода и проверки данных заявки; отправку должен обеспечивать отдельный backend.
11. **Чем CSS-модалка отличается от `dialog`?** CSS-модалка обычно управляется селекторами вроде `:target`; `showModal()` у `dialog` создаёт модальный слой, ограничивает фокус и поддерживает Escape.
12. **Для чего CSS-переменные?** Для повторного использования цветов, отступов и других значений из одного места.
13. **Зачем `:hover` и `:focus-visible`?** Они показывают взаимодействие мышью и положение клавиатурного фокуса.
14. **Для чего Flexbox?** Для раскладки преимущественно по одной оси: меню или содержимое карточки.
15. **Для чего Grid?** Для раскладки строк и столбцов: сетка товаров и каталог с боковой панелью.
16. **Что такое БЭМ?** Методология организации интерфейса и именования классов по блокам, элементам и модификаторам.
17. **Чем блок отличается от элемента?** Блок самостоятельный; элемент описывает часть этого блока.
18. **Чем элемент отличается от модификатора?** Элемент — часть структуры; модификатор — вариант или состояние.
19. **Почему избегают CSS по `id`?** Такой селектор менее удобен для повторного использования и сложнее переопределяется.
20. **Что должно быть в README?** Описание, тема КР, структура, технологии, запуск, ссылки, автор, группа и выполненные доработки.
21. **Что доработано самостоятельно?** FAQ, варианты карточек, подробные описания трёх моделей, сравнение и улучшенный сценарий заявки.
22. **Почему это полезно?** Пользователь может сравнить модели, открыть нужное описание и видеть выбранный товар при заполнении формы.

## Постановка КР 2

КР №2 выполняется в отдельном репозитории `kr2-bootstrap-shop` как версия той же
предметной области на Bootstrap или согласованном альтернативном фреймворке.
Нужны сетка, navbar, card, btn, формы, modal, alert и badge. Это следующая работа:
практика 8 требует познакомиться с её постановкой, а не добавлять Bootstrap в КР №1.


## Результаты локальной проверки

Проверены пять HTML-страниц: по одному `main` и `h1`, уникальные заголовки и `id`,
единая навигация, существование локальных ресурсов и якорей, подписи полей,
базовые классы у модификаторов, отсутствие inline-стилей и CSS по `id`.
Синтаксис `js/main.js` проверен интерпретатором JavaScript.

В браузере просмотрены страницы и таблица, проверены переход из каталога к
описанию товара, FAQ, открытие диалога с выбранным товаром, закрытие Escape,
ошибочный e-mail и телефон, обязательное согласие, успешная проверка формы
на отдельной странице и в диалоге, сброс полей и сообщение о результате.

Для сдачи изменения из веток практик объединяются через Pull Request в `main`.
После завершения публикации Pages проверяются доступность пяти страниц, CSS,
изображения и сценарий заявки по опубликованному адресу.
